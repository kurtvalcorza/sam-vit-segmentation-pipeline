## Conformance notes

_Requirement identifiers in these notes (for example `ST1`, `PAR3`, `DAT24`, `EVAL21`) are the NOTEBOOK_SPEC 1.1 numbering they were written against; NOTEBOOK_SPEC 2.0 renumbered its sections and the pull request that migrated this repository reports conformance against the 2.0 pre-flight checklist (§26) and report format (§30)._

- **Standalone carrier (ST1–ST6):** the primary path performs no clone, repository install, or repository import. Section 2 is `src/sam_vit_segmentation_pipeline/pipeline.py` verbatim (tagged `metadata.dimer.embedded_module`; the only rewrite makes the default weights directory working-directory-relative), Section 3 carries the model identity and the 4-file SHA-256 manifest inline and asserts they agree with the module before anything is fetched, and Section 1 carries the exact `pyproject.toml` runtime pins. `metadata.dimer.generated_from` records the repository, the revision it was generated from, the module SHA-256, and the generator version.
- **Parity (PAR1–PAR4):** `tests/test_notebook_parity.py` and `tools/validate_release_assets.py` fail when the carried module, the inline manifest, or the inline pins differ from the repository, or when the notebook is not byte-identical to the generator's output.
- **Role stages:** `validate_inputs` (DAT24) writes `outputs/sam_vit_segmentation_input_manifest.json` with the schema, ceilings, the input's observed mode and size, how many clicks and whether a box was given, the cleaned prompt values, the verdict, and one recorded rejection finding from the click-outside-image probe; `evaluation_report` (EVAL21) writes `outputs/sam_vit_segmentation_evaluation_report.json` — `sample-sanity` with one `mask_iou` entry per candidate (marking the one the decision rule selected) when a reference mask is supplied, `not-measurable` on BYOD (with what labelled data would make the task measurable).
- The notebook exercises `SAMViTSegmentationPipeline` through the carried module rather than reimplementing model loading; model acquisition goes through that module: `stage_missing_files(WEIGHTS_DIR, allow_download=True)` fetches only the manifest entries a fresh clone lacks (the git-ignored `model.safetensors`), at the pinned revision, `verify_snapshot` re-hashes every entry and returns its summary dict, and `from_pretrained(weights_dir=WEIGHTS_DIR)` loads the verified files (`local_files_only=True`, `trust_remote_code=False`); the notebook never calls `huggingface_hub` or `transformers` directly. No loader notice is expected (the card-pass smoke wrote nothing to stderr). The notebook's only external dependencies are the pinned PyPI distributions and the Hub at that revision.
- The default sample is a synthetic 320×240 scene drawn in code (dark rectangle at [40, 60, 140, 180], red disc at [200, 80, 280, 160]) with one foreground click at (90, 120) — the same scene and click the card-pass smoke used; `mask_iou` of the best candidate against the drawn rectangle's mask and the area comparison are sanity evidence for the prompt, forward pass and up-sampling, not a segmentation metric (mIoU needs labelled masks and is not computed).
- Score semantics: `iou_scores` are the model's own uncalibrated predictions from an unclipped regression head — the smoke returned 1.012 on this scene, and the notebook says a value above 1.0 means only "ranked highest" — not measured overlaps or probabilities; the conventional argmax candidate is used and stated; the pipeline ships no acceptance threshold and the caller owns any decision rule. The notebook performs no validation of its own — image, prompts and `multimask` are checked only by the pipeline's `validate_inputs`/`segment` path.
- Ceilings `MIN_IMAGE_SIDE` (16), `MAX_IMAGE_SIDE` (4096), `MAX_PROMPTS` (16), `NUM_MULTIMASK_OUTPUTS` (3) and `MASK_THRESHOLD` (0.0) are printed before the model runs; one object per call is stated; automatic mask generation, text prompts, mask-input prompts, class labels and video are named as out of scope.
- CPU is documented as adequate (card-measured 3.77 s load after a 0.21 s manifest verification, 2.93 s per click prompt on 320×240; encoder cost fixed by the 1024×1024 working size).
- `USE_BYOD` defaults to `False` so the sample path never opens an upload dialog.
- `tools/validate_release_assets.py` performs source validation only. It does not satisfy the
  clean-runtime execution requirement; a release review must confirm that a recorded clean run in
  `docs/release-verification.md` matches the notebook revision under review before the status is
  promoted to `Release-grade`.
